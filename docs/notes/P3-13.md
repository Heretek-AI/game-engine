## What Avalonia 12.1.4 exposes (verified in the actual assemblies)

Entry point: `Avalonia.Rendering.Composition.Compositor.TryGetCompositionGpuInterop()`
returns `ICompositionGpuInterop` (ref: `Avalonia.Base.xml`, confirmed by
reflection over `Avalonia.Base.dll`):

- `SupportedImageHandleTypes` / `SupportedSemaphoreTypes` (string lists; see
  `KnownPlatformGraphicsExternal*` below — query at runtime, never hardcode).
- `GetSynchronizationCapabilities(handleType)` →
  `CompositionGpuImportedImageSynchronizationCapabilities`
  (`Semaphores | KeyedMutex | Automatic | TimelineSemaphores`).
- `ImportImage(IPlatformHandle, PlatformGraphicsExternalImageProperties)` and
  `ImportImage(ICompositionImportableSharedGpuContextImage)` (same-GPU-context
  fast path, no fd/NThandle round-trip when the engine shares the device).
- `ImportSemaphore(IPlatformHandle)` /
  `ImportSemaphore(ICompositionImportableSharedGpuContextSemaphore)`.
- `IsLost`, `DeviceLuid`, `DeviceUuid` (re-query per frame; fall back on lost).
- Vulkan-specifics ride on `PlatformGraphicsExternalImageProperties.VulkanProperties.Layout`
  (the `VkImageLayout` the engine left the image in).

Display path: `CompositionDrawingSurface.{UpdateAsync,UpdateWithKeyedMutexAsync,
UpdateWithSemaphoresAsync,UpdateWithTimelineSemaphoresAsync}
(ICompositionImportedGpuImage, ...)` + `CompositionSurfaceVisual.Surface`
(`Avalonia.Base.dll` reflection 2026-11-04; `Update*` + `Surface` getter/setter
confirmed, `CompositionSurfaceVisual` is public).

Handle types (`Avalonia.Base.xml`: `KnownPlatformGraphicsExternalImageHandleTypes`,
`...SemaphoreHandleTypes`):

- Linux: `VulkanOpaquePosixFileDescriptor` (image + semaphore).
- Windows: `VulkanOpaqueNtHandle`, `D3D11TextureNtHandle`,
  `D3D11TextureGlobalSharedHandle`; semaphores `VulkanOpaqueNtHandle`,
  `Direct3D12FenceNtHandle`.
- macOS: `IOSurfaceRef` (image), `MetalSharedEvent` (semaphore). XML note on
  `IExternalObjectsHandleWrapRenderInterfaceContextFeature` warns MoltenVK
  `MTLSharedEvent`/IOSurface handles are `__unsafe_unretained` — wrap
  synchronously before destroying the Vk source object.

Per-OS backend that consumes the import (assemblies shipped in the NuGet):

- Linux/X11: `Avalonia.Vulkan.dll` (`IVulkanExternalImage`,
  `IVulkanExternalSemaphore`, `ImportImage/ImportSemaphore`,
  `VkImportMemoryFdInfoKHR`) and `Avalonia.OpenGL.dll` (EGL
  `ImportMemoryFdEXT`/`ImportSemaphoreFdEXT`, `ICompositionImportableOpenGlSharedTexture`).
- Windows: same Vulkan NT-handle path (`VkImportMemoryWin32HandleInfoKHR`,
  `VkImportSemaphoreWin32HandleInfoKHR`) or D3D11 shared-handle path.
- macOS: `Avalonia.Metal.dll` (`IMetalExternalTexture`, `ImportImage`,
  `ImportSharedEvent`).

## Sharing design (engine side, to implement)

1. Engine renders the viewport scene to a dedicated shareable `VkImage`
   (`VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_FD_BIT` Linux /
   `OPAQUE_WIN32_BIT` Windows, exportable IOSurface on macOS via MoltenVK).
2. Export per frame: `vkGetMemoryFdKHR` / `vkGetMemoryWin32HandleKHR` (or
   same-context `ICompositionImportableSharedGpuContextImage` when the engine
   and Avalonia share one `VkDevice` — fastest, no handle export).
3. `interop.ImportImage(handle, props)` → `UpdateAsync` (or the semaphore /
   keyed-mutex / timeline variant per `GetSynchronizationCapabilities`) on a
   `CompositionDrawingSurface` shown through a `CompositionSurfaceVisual` in
   the Scene panel. `ImportCompleted` gates freeing the engine-side handle.
4. CPU fallback stays: `ViewportPresenter.Frame()` → `RenderToBuffer` →
   `WriteableBitmap` lock/`InvalidateVisual`. Use it whenever
   `TryGetCompositionGpuInterop()` returns null (headless/Skia),
   `IsLost`, `SupportedImageHandleTypes` lacks the engine's type, import
   throws, or `ENGINE_REQUIRE_GPU` is unset. Headless goldens
   (`UseHeadlessDrawing=false`) always take this path.

### 1) 1920x1080 timing, real GPU (`engine_viewport_share`, sudo)

```text
[PASS] viewport-share: device init ok
       device: AMD Radeon Graphics (RADV GFX1151)
[PASS] viewport-share: shareable image 1920x1080
[PASS] viewport-share: extent 1920x1080
[PASS] viewport-share: exported fd valid
       exported fd: 6
[INFO] viewport-timing: with-copy avg 1168.955 ms over 10 frames at 1920x1080
[INFO] viewport-timing: without-copy avg 0.002 ms over 10 frames at 1920x1080
[PASS] viewport-share: CPU readback intact
VIEWPORT_SHARE_OK
```

Same binary as the hermes user (llvmpipe) for scale:

```text
       device: llvmpipe (LLVM 19.1.7, 256 bits)
[INFO] viewport-timing: with-copy avg 3.237 ms over 10 frames at 1920x1080
[INFO] viewport-timing: without-copy avg 0.001 ms over 10 frames at 1920x1080
```

Acceptance verdict: **without-copy (0.002 ms) < with-copy (1168.955 ms)
— PASS** on the real GPU. The with-copy side is pathological here, and
the cause is instrumented, not guessed (all probes ran in scratch copies
of the test TU through the public `VulkanDevice::proc()` table — no
second volk copy — and were reverted; `git status` clean before notes):

- Empty one-shot submit+fence: 1.271 ms (queue is healthy).
- GPU `vkCmdFillBuffer` fill-rate ladder on device-local memory:
  0.15 MB → 1.638 ms (first-submit cost), then 2.69 / 10.26 /
  76.59 GB/s — the device copies fast.
- Bare `vkCmdCopyImageToBuffer` of the same 8.29 MB share image:
  2.192 ms; `vkMapMemory` itself: 0.001–0.010 ms.
- Full-capture equivalent (barrier + copy + fence + map + byte loop)
  assembled from public entry points: submit→fence 2.129 ms, map
  0.004 ms, **byte-copy loop 1155.584 ms**.
- Reading the same staging mapping in 1 MB chunks: ~150 ms per MB,
  every chunk, pass after pass (never warms: 4 consecutive full reads
  1189/1164/1172/1164 ms vs a same-size RAM baseline of 1.628 ms).
- CPU write into the same GTT mapping is fast (0.546 ms); GPU copy
  GTT→device-local is fast (0.254 ms). Only the CPU *read* stalls.

Root cause: on this host the driver's host-visible staging heap for the
discrete GPU maps **uncached** (`type[2]`, flags `0x6`, heap 0 = GTT;
no `HOST_COHERENT`-free cached type exists, so the noncoherent probe
reports none available). Every CPU load misses to GTT over the
Lenovo-proxy `/dev/dri` path at a flat ~7 MB/s (256x144 … 1920x1080 all
report 0.007 GB/s) while the GPU idles (`gpu_busy_percent` 0, clocks
pinned 2900 MHz `performance`). An APU Pool/AGP-style cached mapping is
not offered by this RADV/device combo, so `capture_rgba8`'s readback of
an 8 MB frame costs ~1.2 s here. That is a host/driver property, not a
regression: llvmpipe (system RAM staging) reads the same path at
3.237 ms, and the zero-copy half — fd export only, no pixel copy —
costs 0.002 ms on both devices, which is exactly the win P3-13 claims.
Production code path is unchanged by this finding (no fix attempted;
per rule 8 the numbers and the mechanism are recorded instead).
