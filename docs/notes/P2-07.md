# P2-07 engine-player executable — notes

## 2026-11-04 — gate + design

- Gate check: P2-02 (PR #158 merged), P2-03 (PR #195 merged), P2-06
  (PR #200 merged) all on origin/main. samples/HelloCube present.
  No ABI change in this slice (ABI stays 4.17).
- Read docs/PARITY_IMPLEMENTATION_PROMPT.md §2, §6 P2-07, §7, §8.
- No open PR touches engine_abi.h (only dependabot #196 open) — no ABI
  minor to consume; none needed anyway.
- Design hinge: the spec says "loads the game assembly through the
  existing dotnet_host" but defines no game-side bootstrap entry point,
  and samples/HelloCube exports no UCO entry at all (its Program.cs is a
  `dotnet` host that loads engine_core, not the reverse) and registers
  no Flecs systems (Spinner.Tick never binds — the golden is a static
  cube after one propagate).
- Resolution: the player tries `Game.Bootstrap.Main` ([UnmanagedCallersOnly]
  UCO, `Game.Bootstrap, <AssemblyName>`) via dotnet_host when
  project.json names a gameAssembly; missing assembly/config/entry is
  NOT fatal — falls back to a native HelloCube-equivalent demo frame
  (camera eye (0,0,3), P4-03 shadow toggle on, tan cube (0.85,0.5,0.2))
  so the acceptance command renders the golden. A loadable startScene
  (scene_load rc >= 0) or a successful bootstrap suppresses the demo.
  When issue and prompt differ, this is the stricter reading that keeps
  exit-0 + golden deterministic; P2-08 can add scenes/bootstrap on top.
- `--autoplay` is NOT implemented here: the P2-08 slice owns that flag
  ("implement the flag in THIS slice if P2-07 didn't").

## Gotchas hit

- renderer_create registers Engine.Runtime.* components on the world;
  player registers through the ABI only, never native headers (ABI
  boundary).
- renderer_frame pumps SDL, runs render_world, presents; world_frame +
  world_propagate are the player's job each frame (P2-03 + M1-03).
- API table types are C typedefs without `struct` qualification in C++;
  include engine_abi.h inside `extern "C"`-free normal C++ (header
  handles linkage itself).
