- Verified facts (Dock 12.1.0.13, `Dock.Model.Mvvm.Factory` + `DockSerializer`):
  - `factory.Tool(out var console, t => t.WithId(...).WithTitle(...))` builds tools;
    `factory.ToolDock(..., Alignment.Left, ...)` / `ProportionalDock` /
    `RootDock` compose the layout; `factory.InitLayout(layout)` wires owners.
  - `factory.MoveDockable(bottom, left, console, inspector)` reparents a tool
    into another dock's tab group; the serialized JSON differs (`movedDiffers`).
  - `new DockSerializer(typeof(ObservableCollection<>))` round-trips the moved
    layout byte-identically (`roundtrip=identical`).
  - `Context` is `[IgnoreDataMember]` on the MVVM model: it never reaches the
    JSON. `InitLayout` re-fills null Contexts from `ContextLocator[id]`, so the
    factory map is the restore path for panel payloads.
- Deviation from prompt §6: the spike used `Dock.Model.Mvvm` (code-first
  factory) rather than `Dock.Model.Avalonia`. The editor slice switched to
  `Dock.Model.Avalonia` because its `AvaloniaDockSerializer` allow-lists only
  known dock properties (no Avalonia `Resources`, no Control payloads), so
  plain `DockSerializer` output stays loadable.

## 2026-11-03 — Blank DockControl: two root causes, both fixed

- Symptom: `editor_shell_1280x720.png` was a blank white window with only the
  menu bar; `shell: all panels in visual tree` FAILED.
- Cause 1 (no theme): `App` registered only `FluentTheme`. Dock's
  `ToolControl`/`ToolDockControl`/tab-strip templates live in
  `DockFluentTheme` (`Dock.Avalonia.Themes.Fluent` package, not previously
  referenced). Without it the `DockControl` renders nothing.
  - Fix: added `Dock.Avalonia.Themes.Fluent` 12.1.0.13 (+ `Dock.Model.Avalonia`
    12.1.0.13) to `Engine.EditorApp.csproj`; `App.Initialize()` adds
    `DockFluentTheme`. Newest packages that can render the Fluent dock theme.
- Cause 2 (Context ≠ view): the factory set `tool.Context = panelControl`,
  but Dock renders `IToolContent.Content`, not `Context`. `Context` is the
  *view-model* slot, resolved to a view through `Application.DataTemplates`.
  No DataTemplate matched a `Border`, so every tab body was empty.
  - Fix: `EditorDockFactory` keeps the model payload-free (no Control in
    Content/Context — SystemTextJson has no metadata for `Border` and
    `Save()` throws `NotSupportedException` otherwise) and exposes
    `EditorViewLocator : IDataTemplate`, registered on the window via
    `DataTemplates.Add(layouts.Factory.CreateViewLocator())`. It returns the
    same panel instance per tool id; Dock's `ControlRecyclingDataTemplate`
    detaches the Control from the old parent (`TryDetachFromParent`) so tab
    moves and layout restores re-parent the live panels.
  - Serialization: `EditorLayoutService.Serialize()` clears tool Contexts
    before serializing and restores them after (panel Controls are never in
    `layout.json` — only ids/arrangement). `Deserialize()` calls
    `_factory.InitLayout(restored)`, which re-fills Contexts from
    `ContextLocator`, then the ViewLocator maps id → Control at render time.
- References (read, not relied on alone — rule 6 is satisfied by the XML docs
  + the running spike + the green headless run below):
  - `Dock` repo `samples/Notepad` (MVVM factory, ViewLocator, NotepadFactory)
  - docs: "Document and Tool Content Guide", "Quick Start" (ViewLocator +
    `DockFluentTheme` in `Application.Styles`)

## 2026-11-03 — Panel close semantics (spec wording)

- Spec says panels "can be dragged, tabbed, floated and closed". All tools
  are `CanClose = true`; closing removes the tool from the layout (Dock
  default: `VisibleDockables.Remove`). `Window > Reset Layout` rebuilds the
  default via `layouts.ResetLayout()` → `DockView.Layout = ...`, so a closed
  panel is recoverable. No per-panel close test added: headless close-button
  clicks go through Dock adorner chrome (not scriptable via the documented
  input APIs in §4.5); the closable flag + Reset path cover the contract.
